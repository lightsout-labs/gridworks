# Architecture

Status: Approved

How Gridworks is built. What it must do is in
[requirements.md](requirements.md). Reasons for the decisions that are costly
to reverse are in the ADRs under `docs/adr/`. This document holds what spans
modules; the decisions inside one module are in `docs/design/<module>.md`.

## Overview

Gridworks is a static single-page application in two parts. The **engine** is
plain TypeScript with no DOM dependency: it owns the workbook, executes
every edit as a command, recalculates formulas, and reads and writes files.
The **app** is the browser side: a canvas that draws the grid, React
components for everything around it (ribbon, formula bar, sheet tabs,
dialogs), and one platform module that is the only code allowed to touch
files, storage, the clipboard and printing. When the user types in a cell,
the grid passes the text to the app, the app sends a `setCell` command to
the workbook, the workbook parses the input, stores it, records the inverse
for undo, marks dependent cells dirty and notifies its listeners; the grid
repaints the visible cells, reading each one from the workbook (which
calculates a dirty cell when it is read), and the app asks the platform to
record the command in browser storage at once and to save the changed
sheet a moment later.

## Stack

| Concern | Choice | Why |
|---|---|---|
| Language | TypeScript, strict mode | Constraint. |
| Build and dev server | Vite | Static output for GitHub Pages; sub-path via `base` (R49). |
| UI around the grid | React | The ribbon, menus and dialogs are many stateful controls; see [ADR 0002](adr/0002-canvas-grid-react-chrome.md). |
| Grid | One HTML canvas, drawn by our own code | Only a virtualized canvas meets R45; see [ADR 0002](adr/0002-canvas-grid-react-chrome.md). |
| Menus, dialogs, tooltips, tabs | Radix UI primitives, unstyled | Correct focus, keyboard and dismissal behavior for R38 and R44 without writing it; all styling stays ours (R43). |
| Styling | CSS Modules and CSS custom properties | Themes are two sets of variables (R42); no styling library needed. |
| Icons | Lucide | The single consistent icon set of R43. |
| Fonts | The system UI font stack | Works offline (R35) and loads nothing. |
| Formula engine and workbook model | Our own | See [ADR 0001](adr/0001-own-formula-engine.md). |
| Number formats and input recognition | `numfmt` | Implements Excel format codes and value parsing (R4, R18). |
| `.xlsx` | Our own reader and writer over JSZip | See [ADR 0006](adr/0006-own-xlsx-reader.md) and [ADR 0007](adr/0007-own-xlsx-writer.md). |
| `.csv` | Our own reader and writer | About a hundred lines; no dependency justified (R32). |
| Threads | Main thread only, recalculation on demand | See [ADR 0004](adr/0004-main-thread-lazy-recalculation.md). |
| Browser storage | IndexedDB, used directly | Holds large workbooks; the few calls needed do not justify a wrapper (R33). |
| Offline | A service worker generated by `vite-plugin-pwa`, with no web app manifest | Precaches the build output (R35); installable PWA packaging is out of scope. |
| Translation | Our own `t(key)` over two dictionaries | Two languages and plain strings need no library (R41). |
| Unit tests | Vitest, Node environment for the engine | Running the engine tests in Node demonstrates R50. |
| End-to-end tests | Playwright on Chromium, Firefox and WebKit | The supported browsers (Constraints). |
| Lint and format | ESLint, Prettier, `tsc --noEmit` | ESLint also enforces the module boundaries below. |
| Package manager and runtime | npm and the current Node.js LTS, pinned in `.nvmrc` | The default; nothing needs more. |
| Hosting | GitHub Pages, deployed by GitHub Actions | Constraint (R49). |

There is no state management library: the workbook is the store, and React
reads it with `useSyncExternalStore`.

Boundaries, enforced by the build so that R50 and R51 cannot erode:

- `src/engine` compiles with its own `tsconfig` that excludes the DOM
  library, and ESLint forbids it from importing `src/app`.
- ESLint forbids `indexedDB`, `localStorage`, `navigator.clipboard`,
  `clipboardData`, the copy command, listeners for the copy, cut and paste
  events, `window.print`, file inputs and download links everywhere except
  `src/app/platform/web`. A desktop shell such as Tauri or Electron would
  add a second implementation of `Platform` beside it and reuse everything
  else.

The decisions inside one module, each with its reason, are in that module's
design file: [engine/workbook](design/engine/workbook.md),
[engine/formula](design/engine/formula.md),
[engine/format](design/engine/format.md), [engine/io](design/engine/io.md),
[app/platform](design/app/platform.md), [app/grid](design/app/grid.md) and
[app/ui](design/app/ui.md).

Decisions that span modules, cheap to reverse, with their reasons:

- **Every edit is a command.** The app changes the workbook only through
  `execute`, and the workbook records the reverse of each command before
  it runs it, so undo covers every change by construction (R5) rather
  than feature by feature. Undo and redo run a command too, and the
  listeners receive it like any other, so storage records an undo as a
  change. A workbook opened with its recorded changes replayed
  (`fromSnapshot(snapshot, changes)`) starts with nothing to undo, as the
  history is not stored.
- **A command that reads cells is recorded as what it did.** A paste, a
  fill, a sort and a replace reach the listeners, and undo, as a `group`
  of `restore` commands of the cells they changed, so replaying a recorded
  one does not read its source again (a value pasted from `TODAY()` stays
  the same), and undo needs nothing of its own.
- **Copy and paste go through the system clipboard.** Ctrl/Cmd+C, X and V
  are not shortcuts but the browser's clipboard events, which the
  platform hears. A copy or cut remembers the range in the view and puts
  its cells, as they are shown, on the clipboard as tab-separated text and
  an HTML table, as Excel does. The Cut and Copy buttons and menu items do
  the same through `writeClipboard`. A paste reads the plain text: if it
  is the text of the cells copied, Gridworks pastes those cells, formulas
  and formats and all; any other text, from another application, is a
  `setCells` command that sets the cells from the top left of the
  selection as if each were typed (R4), a row for each line and a cell
  for each tab, with Excel's quoting. The HTML of other applications is
  not read: Excel and Google Sheets put the same cells on the clipboard as
  text. The Paste button and menu item paste only the cells copied in
  Gridworks, since reading the clipboard from a button needs a permission.
- **Dates are Excel serial numbers** with a date format, as in Excel, so
  date arithmetic and `.xlsx` round trips need no conversion.
- **Number and date formats do not change with the interface language.**
  R41 covers the interface only; one behavior keeps files and tests the
  same in both languages. Function names stay in English in both languages,
  as they are in `.xlsx` files.
- **A theme is a set of CSS custom properties**, chosen by the `data-theme`
  attribute of the root element, and every color of the interface is one of
  them (R42, R43). The canvas reads the same properties when it paints and
  repaints when the attribute changes, so the grid needs no theme of its
  own.
- **Cell fonts are a fixed list of fonts present on Windows and macOS**
  (Arial, Courier New, Georgia, Times New Roman, Trebuchet MS, Verdana),
  each with fallbacks for Linux, so that nothing is downloaded. A cell
  without a font has the interface's system font, and sizes are in points
  with 10 as the default, drawn at 4/3 pixels a point. The workbook gives
  the list as `FONTS`, so that the grid, the ribbon and the files share it.

## Data

A workbook **snapshot** is a versioned, JSON-compatible object: workbook
properties (name, sheet order, named ranges, the table of distinct styles)
and, for each sheet, its name and tab color, its columns of values, style
identifiers, formulas, row heights and column widths, hidden rows and
columns, merges, frozen
panes, filters, validation rules, conditional formats, notes and
hyperlinks. It is the only form in which a
workbook leaves the engine.

- **Browser storage**: an IndexedDB database named `gridworks` with three
  object stores. `workbooks` holds one record for each workbook
  (identifier, name, modification time, workbook properties, defined
  names). `sheets`
  holds one record for each sheet, keyed by workbook and sheet identifier,
  so that autosave can rewrite only the sheets that changed; for now it
  rewrites them all, after deleting those of the workbook, so that a
  deleted sheet leaves no record. `changes` holds
  each command executed since the workbook was last saved, keyed by
  workbook and sequence number. Each command is recorded the moment it is
  executed; the whole workbook is saved half a second after the last change
  and when the page is hidden, and that save deletes the changes it
  includes. Opening a workbook replays its changes over its last save.
  See [ADR 0005](adr/0005-record-each-change-then-save-snapshots.md).
- **Preferences** (language, theme): through `Platform.preferences`, stored
  in `localStorage` by the web implementation, under `gridworks.language` and
  `gridworks.theme`. Without a stored choice the language is that of the
  browser and the theme that of the system.
- **Files**: `.xlsx` and `.csv`, converted to and from a snapshot by
  `engine/io`. Undo history is not stored.

## Repository layout

```

src/engine/formula/      Parser, evaluator, and the function library, a file per family
src/engine/format/       Number formats and input recognition
src/engine/io/           XLSX and CSV
tests/xlsx.ts            Builds .xlsx files laid out as Excel writes them, and a workbook with every feature of R30, for tests
tests/formula.ts         Evaluates formulas over cells named as in A1, for tests
src/app/platform/        Platform interface
src/app/platform/web/    The web implementation
src/app/grid/            Canvas grid and the view state
src/app/ui/              React shell, dictionaries, themes
src/main.tsx             Entry point: creates the web platform, mounts App
tests/e2e/               Playwright tests
tests/boundaries.test.ts Checks that lint enforces the module boundaries
scripts/check-docs.py    Document checker, copied from nightshift
docs/                    Requirements, architecture, module design, ADRs, backlog
.github/workflows/       CI and deployment
```

Unit tests sit beside the code they test, as `*.test.ts`. In `src/app`, code
that touches the DOM is in `.tsx` files or in `src/app/platform/web` and is
covered by the end-to-end tests; every other `.ts` file there has no DOM, is
unit tested, and counts toward the coverage floor.

## Make targets

| Target | Contents |
|---|---|
| `make check` | `prettier --check`, `eslint`, `tsc --noEmit` for both the engine and the app configuration, `vitest run --coverage` with a floor of 90% of lines in `src/engine` and in the parts of `src/app` that have no DOM, `scripts/check-docs.py` |
| `make e2e` | Builds the production bundle, serves it with `vite preview` under `/gridworks/`, and runs the Playwright tests against it |
| `make perf` | The time limits of R45–R47 in `tests/perf`: the engine's with Vitest, then the app's with Playwright on Chromium against the production bundle, one test at a time |

CI runs all three on every pull request: `check` and `e2e` as required
checks, and `perf` as a check that does not block a merge, because a shared
CI machine is slower, and varies more, than the laptop the time limits are
set for. A `perf` failure is confirmed or dismissed by running `make perf`
on such a laptop. The `e2e` check passes when each of four shards of the
end-to-end tests, run on machines of their own in parallel, has passed. The
shards and `perf` run in Playwright's container image, whose browsers and
their system libraries come installed, at the version of `@playwright/test`
in the lock file; a change to that version changes the image too.

## Testing

| Level | Covers | How |
|---|---|---|
| Unit | The engine through its four interfaces: every command and its undo, every function against results taken from Excel's documentation, reference rewriting, recalculation, number formats, XLSX and CSV round trips | Vitest in the Node environment, with no DOM available |
| Unit | App logic that needs no browser: grid geometry, selection and keyboard navigation, the status bar summary, translation completeness for both languages, shortcut tables, the printable document | Vitest |
| End to end | Each slice's user flow in the built app: keyboard and mouse on the grid, the ribbon, menus and dialogs, storage across reloads, file open and save, both themes and languages, offline use | Playwright on Chromium, Firefox and WebKit |
| End to end | The system clipboard (R7), with another application played by a text box outside the app; each browser has a clipboard of its own, so these tests run in parallel with the others | Playwright |
| Time limits, unit | Recalculating a chain of 100,000 formulas within a second (R46) and opening a 10 MB file within 5 seconds (R47), in the engine | Vitest, `make perf` |
| Time limits, end to end, Chromium only | Scrolling speed (R45), measured as the time to draw each frame, one scroll step a frame, while scrolling a sheet of 100,000 by 100 populated cells stored directly in IndexedDB; every frame must draw within 16 ms. Recalculation time (R46): a chain of 100,000 formulas, stored the same way, whose start is edited, with input going on meanwhile | Playwright, `make perf` |

Two requirements cannot be fully checked by automated tests and are checked
by the human at release acceptance: that files saved by Gridworks open in
Microsoft Excel itself (R30), and the 60 frames per second on a mid-range
laptop (R45). The automated tests cover them as far as they can: files
built by `tests/xlsx.ts` with the parts and markup that Excel writes,
round trips through the writer and reader, and a frame-time budget in
`make perf`.

## Deployment

The app runs at `https://lightsout-labs.github.io/gridworks/`. A GitHub Actions
workflow runs on every push to `main`: it builds the production bundle with
the base path `/gridworks/`, publishes it with the GitHub Pages actions, and
then runs one Playwright smoke test against the live address, which loads
the app, enters a formula and checks the result. It is the end-to-end test
tagged `@smoke`, run with `GRIDWORKS_URL` set to the live address and
`GRIDWORKS_COMMIT` to the deployed commit, which the test waits to be served. A failed smoke test fails
the workflow. A release is verified by that smoke test and by the human's
acceptance of the deployed app.
